# Hardware-Aware Energy-Efficient LLM Inference

This research codebase studies **energy-aware adaptive self-speculative decoding** on consumer hardware. The main experiment uses the pretrained **LayerSkip Llama 3.2 1B** model. It compares ordinary greedy decoding, fixed speculative settings, intermediate-exit observation policies, and request-level adaptive selection driven by measured energy or latency.

**Research question:** Can a pretrained LayerSkip model produce exactly the same greedy tokens as ordinary full-model decoding while using less measured GPU energy and time on consumer hardware?

**Headline result:** In the latest saved CUDA run, all **381/381** measured requests matched native greedy output. The adaptive policy measured **35.3% lower GPU energy per token** and **42.3% lower latency per token** than ordinary decoding. These are descriptive results from one workload on one device, not established general savings.

> **What this does not show yet:** The adaptive policy bought no observations during held-out requests, so the run does not show that selective feedback caused the savings. It also has not yet been compared against a fixed depth-12 / draft-3 baseline, which is the action it chose for 47 of 48 requests.

## Key terms

| Term | Meaning |
|---|---|
| Layer / depth | A stage in the transformer. A smaller exit depth uses fewer layers to draft. |
| Draft | Tokens tentatively generated by the early layers. |
| Verification | The remaining layers check the draft against the model's ordinary greedy behavior. |
| Accepted prefix | The initial run of draft tokens that verification agrees with. |
| Rollback | Removing the rejected draft suffix from the key/value cache. |
| Observation / feedback | A prediction from an intermediate exit, recorded so the controller can learn about an action. |
| Greedy output | At each step, the token with the highest model score. |
| Exact match | Generated token IDs equal native greedy token IDs. This checks output equivalence, not answer quality. |
| J/token, s/token | Total measured request energy or time divided by generated tokens. GPU experiments measure the GPU only. |

## Methods

The central method is **self-speculative decoding**: the model drafts tokens with its own early layers, then verifies them with its remaining layers. A controller decides whether and how to speculate. The other methods address different costs and are evaluated separately; they are not one combined algorithm.

| # | Method | What it changes | Role |
|---:|---|---|---|
| 1 | Native greedy | Nothing | Correctness and cost reference |
| 2 | Fixed self-speculation | Decoding (fixed depth/draft) | Fixed-action baseline |
| 3 | Adaptive selector | Action choice per request | Proposed controller |
| 4 | Selective feedback | Extra intermediate-exit information | Optional input to the selector |
| 5 | Executed-cost bandit | Action choice per request | Controller baseline |
| 6 | DEL comparison | Action choice and draft stopping | External adaptive-decoding baseline |
| 7 | Engine optimization | Implementation | Faster execution for all paths |
| 8 | Memory optimization | Implementation | Lower working memory |
| 9 | FP16 precision | Numeric precision | Separate execution condition |

### 1. Native greedy decoding (reference)

The full model generates one token at a time, appending each token and running the full model again. Every candidate method is checked against this exact token sequence.

**Result (latest FP32 run):** 4.129220 GPU J/token and 0.105173 s/token. FP16 runs use different workloads, so their ordinary baselines are not comparable to this number.

### 2. Fixed LayerSkip self-speculation

1. Choose an exit depth and draft length (for example, depth 4 and one draft token).
2. Draft tokens with the early layers.
3. Verify the draft with the remaining layers.
4. Keep the matching prefix, roll back rejected tokens, and use the full model's correction token.
5. Repeat.

If enough draft tokens are accepted, the model commits several tokens for less work than running the full model once per token. If acceptance is low, drafting and verification add work. A setting can also mismatch greedy output if verification or cache handling does not preserve exact decoding.

**Result:** In a 16-token FP16 confirmation sweep, depth 4 / draft 1 measured **11.7% lower GPU energy** and **13.1% lower latency** than ordinary decoding, with exact greedy matches. Depths/drafts (8, 1), (4, 2) and (8, 2) mismatched. In 100- and 200-token FP16 runs, depth 4 / draft 1 also mismatched, so its lower cost there does **not** count as an exact-output improvement.

### 3. Adaptive selector

The controller chooses between ordinary decoding and speculative actions (depth plus draft length) using observed execution costs. It can also pay for intermediate-exit observations when it expects the information to justify the cost. Paid observations are available only for depth 8 / draft 3, after sufficient paired calibration. The selector is a **heuristic** with no formal optimality guarantee.

**Result (latest FP32 run):** 2.671720 GPU J/token and 0.060672 s/token, versus 4.129220 J/token and 0.105173 s/token for ordinary decoding. It chose depth 12 / draft 3 for 47 of 48 held-out requests and depth 8 / draft 3 for one, and bought no held-out observations.

This is the strongest result for adaptive self-speculation as a whole. Because the controller mostly chose one action, it does not show that adaptation beats a fixed depth-12 / draft-3 policy on the same requests.

### 4. Selective intermediate-exit feedback

During speculative work, the system can record predictions from intermediate exits using hooks and projections, not an extra full forward pass. Projecting to vocabulary scores, computing confidence, and synchronizing still cost time and energy.

| Mode | Behavior |
|---|---|
| Never observe | No extra observations |
| Selected observe | Feedback from one chosen exit |
| Always observe | Feedback from every configured exit |

Only observations aligned with the **committed prefix** count. Predictions conditioned on a rejected draft branch are not valid evidence for later tokens, so invalid and post-stop observations are filtered out.

**Result (latest FP32 run):** Selected observation measured 3.112311 J/token and always observation 3.214446 J/token, both above never-observe at 2.764236 J/token. Median paired observer overhead was **21.680 J/request** (selected) and **28.613 J/request** (always). Serving-time observation did not repay its cost here. Feedback may still help during calibration, but this experiment does not isolate that contribution.

### 5. Executed-cost bandit

An independent-arm bandit treats each decoding action as an arm, runs it, measures the real cost, and favors cheaper arms. It is a comparison for the adaptive selector, which uses its own heuristic and can consider feedback.

**Result (latest FP32 run):** 2.791580 J/token and 0.065241 s/token, versus 2.671720 J/token and 0.060672 s/token for adaptive. Both beat ordinary decoding on this workload. The action sets and fixed baseline are not yet matched closely enough to attribute the gap to the controller.

### 6. DEL adaptive-decoding comparison

A local port of DEL tracks decayed acceptance and confidence statistics, chooses an exit using a stated objective, stops drafts dynamically, and updates only from valid committed context. It is an external baseline, not part of the adaptive controller.

**Result (pilot, 97 requests, all matched greedy):**

| Policy | GPU J/token | s/token |
|---|---:|---:|
| DEL (local port) | 4.714074 | 0.093979 |
| Adaptive | 3.658246 | 0.076396 |
| Fixed depth 12 | 3.452809 | — |

Adaptive beat DEL in this pilot but was **worse than the fixed depth-12 baseline**. This is a local port, not a reproduction of the upstream implementation or its published results.

### 7. Decoder-engine optimization

Implementation changes that do not alter the decoding policy:

- Reuse rotary positional embeddings across layers.
- Skip all-ones attention masks when inputs have no padding.
- Keep token tensors on the device to avoid repeated uploads.

**Result:** Pinned before/after comparison against revision `71b0a23` (FP16 CUDA, 8 prompts, 3 repeats, 16 tokens; all 96 requests matched greedy). Ordinary decoding: **15.5% lower latency**, **10.3% lower GPU energy**. Depth 4 / draft 1: **13.8% lower latency**, energy effectively unchanged. This was a different software state from the latest adaptive run, so these gains should not be added to the adaptive result without a controlled combined experiment. See [engine optimization report](hardware_aware_selective_feedback/results/engine-optimization/rtx3050-engine-optimization-final.md).

### 8. Memory optimization

Projects only the final prompt position into vocabulary scores and releases unneeded forward outputs early. It targets peak memory, not compute or selector choices.

**Result:** FP16, 8 prompts, 2 repeats, 32 tokens; all 64 requests matched greedy. Working memory fell about **66%** (62.44 to 21.12 MiB), but total peak allocation fell only **41.32 MiB (1.7%)** because model weights dominate. Energy per token rose about **0.3%**, so this is a memory improvement, not an energy improvement. See [memory optimization report](hardware_aware_selective_feedback/results/memory-optimization/rtx3050-memory-optimization.md).

### 9. FP16 precision

FP16 stores and computes values at lower precision than FP32, which can reduce memory and speed up suitable GPUs. It can also change outputs, so each precision/configuration needs its own exact-token check.

**Result:** FP16 runs show lower absolute costs, but they are not a controlled precision-only comparison with FP32 because workloads differ. Several longer speculative FP16 configurations mismatched greedy output. FP16 is **not** established as an exact-output efficiency improvement.

## How the methods fit together

```text
Native greedy
  └─ correctness and cost reference

LayerSkip self-speculation
  ├─ fixed depth/draft ........ fixed-action baseline
  ├─ adaptive selector ........ chooses actions from measured costs
  ├─ cost bandit .............. alternative selection baseline
  ├─ DEL ...................... external adaptive-decoding baseline
  └─ intermediate feedback .... optional information for selection

Engine optimization ─┐
Memory optimization ─┼─ implementation/execution changes, evaluated separately
FP16 precision ──────┘
```

- **Feedback is not self-speculation.** Self-speculation drafts and verifies tokens; feedback records extra information about intermediate exits.
- **The selector is not the engine optimization.** The selector chooses actions; engine changes make execution cheaper.
- **DEL and the bandit are comparisons**, not components of the proposed method.

| Setting | Recorded value |
|---|---|
| Hardware / OS | NVIDIA GeForce RTX 3050 Laptop GPU / Windows 11 |
| Precision / device | FP32 / `cuda:0` |
| Runtime | PyTorch `2.9.0+cu130`, Transformers `5.18.0` |
| Objective / sensor | Energy / NVML cumulative GPU energy counter (mJ converted to J) |
| Measurement boundary | NVIDIA GPU, not the whole laptop |
| Prompt split | 8 calibration and 16 held-out prompts, equally divided between GSM8K and HumanEval |
| Held-out repeats / token limit | 3 repeats / 64 maximum generated tokens |
| Observer calibration | 6 pairs per observation mode across 6 distinct calibration prompts |

### Experiment procedure

1. Load `facebook/layerskip-llama3.2-1B` at pinned revision `81deb0f88734409cca506bcefcfb5c6bd2667565`.
2. Load pinned GSM8K and HumanEval prompts with disjoint calibration and held-out IDs, truncated to 192 tokens.
3. Calibrate ordinary decoding and speculative actions with exit depths 4, 8 and 12 and draft lengths 1 and 3. Measure observer overhead with paired executions.
4. Run seven policies on the same held-out prompts, randomizing policy order within each prompt/repeat. The adaptive selector and bandit keep learning from their own executed requests.
5. Compare every output with native greedy token IDs and save raw measurements, comparisons and summaries.

| Policy | Behavior |
|---|---|
| `ordinary` | Ordinary full-model greedy decoding |
| `fixed` | Exit depth 4, draft length 3, no observers |
| `never_observe` | Exit depth 8, draft length 3, no observers |
| `selected_observe` | Exit depth 8, draft length 3, observe exit 4 |
| `always_observe` | Exit depth 8, draft length 3, observe exits 4 and 12 |
| `bandit` | Independent-arm cost bandit using executed costs |
| `adaptive` | Cost-aware heuristic selecting a decoding action and, when justified, paid observations |

There are 45 calibration requests and 336 held-out requests (48 per policy). Each policy generated 3,072 held-out tokens. The run used FP32 and `--attn auto` (SDPA on CUDA). Quantization, compilation, adaptive draft lengths, context-specific selection, CUDA Graphs and GPU clock/power pinning were disabled.

| Policy | Runs | Latency (ms/token) | GPU energy (J/token) | Greedy mismatches |
|---|---:|---:|---:|---:|
| `ordinary` | 48 | 105.173 | 4.129220 | 0 |
| `fixed` | 48 | 64.210 | 2.784979 | 0 |
| `never_observe` | 48 | 63.219 | 2.764236 | 0 |
| `selected_observe` | 48 | 70.298 | 3.112311 | 0 |
| `always_observe` | 48 | 72.359 | 3.214446 | 0 |
| `bandit` | 48 | 65.241 | 2.791580 | 0 |
| `adaptive` | 48 | 60.672 | 2.671720 | 0 |

Per-token values are total measured request cost divided by total generated tokens, not medians of per-request ratios. Measurements include prefill and generation; model loading, native-greedy reference generation, and selector decisions outside the measured call are excluded.

Compared with ordinary decoding, adaptive measured 35.3% less GPU energy per token, 42.3% less time per token, and 1.73x throughput. Calibration consumed **8,991.701 J** separately; that cost is not amortized into the table.

## Findings, limits and novelty

**Finding:** For one RTX 3050 FP32 workload, adaptive self-speculative decoding measured 35.3% lower GPU energy and 42.3% lower latency than ordinary greedy decoding, with 381/381 exact token matches.

**Limits:**

- GPU energy only, not whole-laptop energy.
- One model, one device, 16 held-out prompts and 64-token outputs.
- No task-quality scoring: HumanEval code is neither executed nor scored, and greedy agreement checks equivalence, not correctness.
- No held-out observations were bought, so feedback is not shown to cause the savings.
- No fixed depth-12 / draft-3 baseline on the same held-out prompts.
- Calibration energy is not amortized.

**Novelty:** The results do not establish a proven novel algorithm. The candidate contribution is a measured-cost controller for selecting self-speculative decoding actions, with committed-prefix filtering of feedback and optional cost-aware observation.

**Next experiment needed:** Keep the action space and controller fixed, then compare no feedback, selective feedback and always-on feedback, plus a fixed action chosen from calibration data, on the same held-out prompts.

## Setup

Run commands from the repository root. Use a virtual environment and install a PyTorch build for your hardware, then the root dependency file:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

On macOS/Linux, activate with `source .venv/bin/activate`. The Windows NVIDIA helper creates a Python 3.12 environment when needed and installs the CUDA 12.4 PyTorch stack:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\setup_cuda_3050.ps1
.\.venv\Scripts\Activate.ps1
python -m prototype.doctor
python -m hardware_aware_selective_feedback.run --probe --device cuda
```

> **Reproducibility gap:** `requirements.txt` pins PyTorch `2.6.0` and Transformers `4.50.0`, but the latest report records `2.9.0+cu130` and `5.18.0`. Installing the dependency file does not recreate that environment. Record runtime versions with results and recheck correctness when changing them.

The LayerSkip checkpoint requires authorized Hugging Face access. After access is granted, run `hf auth login`. A missing snapshot downloads into the ignored `layerskip/cache/` directory. Never commit credentials or model weights. No local training or llama.cpp is required.

## Run the experiment

Command used for the latest saved results:

```powershell
python -m hardware_aware_selective_feedback.run `
  --device cuda `
  --objective energy `
  --calibration 4 `
  --test 8 `
  --tokens 64 `
  --repeats 3 `
  --observer-pairs 6
```

`--calibration` and `--test` count prompts **per dataset**. `--tokens` is the maximum output length; generation can stop at EOS. PowerShell uses backticks for line continuation; other shells can run the command on one line.

Default outputs are `hardware_aware_selective_feedback/results/latest.json` and `latest.md`. Use `--output path/to/run.json` to keep an existing report; the Markdown report is written beside it.

Start with a separately saved smoke run on a new environment:

```powershell
python -m hardware_aware_selective_feedback.run --device cuda --objective energy --calibration 1 --test 1 --tokens 4 --repeats 1 --observer-pairs 1 --output hardware_aware_selective_feedback/results/smoke/local-check.json
```

FP32 is the default. `--precision fp16` reduces memory on CUDA, but FP16 runs have recorded greedy mismatches. By default, mismatches are recorded and the affected configuration is excluded from adaptive/bandit selection; fixed baselines may still run it. Add `--stop-on-mismatch` to abort instead. To inspect mismatches:

```powershell
python -m hardware_aware_selective_feedback.diagnose_mismatch --report hardware_aware_selective_feedback/results/latest.json
```

### Device and energy support

`--device auto` tries CUDA, Intel XPU, macOS MPS, then CPU. Device availability alone does not validate the custom decoding path.

| Device / platform | Built-in cumulative energy source |
|---|---|
| NVIDIA CUDA | NVML GPU energy, when supported |
| Linux CPU | Readable RAPL CPU-package counters |
| Windows CPU | Readable EMI V2 `_PKG` channels, when available |
| XPU or macOS CPU/MPS | No built-in per-request energy counter |

`--objective energy` requires a working counter. `--objective auto` falls back to latency and records `energy_j: null`. An external meter can supply a cumulative text counter with `--energy-source file --counter-file <path> --counter-unit joules --energy-scope <scope>`. Compare energy only across equivalent measurement boundaries. See the [experiment README](hardware_aware_selective_feedback/README.md) for sensor details.

### Optional experiments

| Option | Purpose / current scope |
|---|---|
| `--adaptive-drafts` | Shorten drafts below 50% recent acceptance; fall back below 30% with periodic probes |
| `--context-selector` | Use dataset- and prompt-length-specific selector costs after enough observations |
| `--quantize int4` / `int8` | Optional bitsandbytes weight quantization on CUDA |
| `--compile` | Optional `torch.compile` model wrapper |
| `--attn` | `auto`, `sdpa`, `eager` or `flash_attention_2` |
| `--cuda-graph-drafts` | Prototype static-cache draft replay; CUDA only, incompatible with `--compile` and `--quantize` |
| `--gpu-clock-mhz`, `--gpu-power-limit-w` | Apply GPU settings during execution and restore them afterward; needs admin/root and hardware support |

These options were not used in the latest run and carry no measured improvement claim here. Recheck greedy agreement after changing precision or execution settings. See [efficiency implementation notes](EFFICIENCY_CHANGES.txt).

To compare a fixed grid without observers, use the paired sweep. Its precision defaults to FP16; this example uses FP32:

```powershell
python -m hardware_aware_selective_feedback.sweep --device cuda --precision fp32 --test 4 --tokens 16 --repeats 2 --output hardware_aware_selective_feedback/results/fixed-sweep/local-fp32.json
```

The default sweep covers depths 4/8/12 and draft lengths 1/2/3/4 plus ordinary decoding. `--batch-sizes 2 4` adds batched ordinary baselines; batched speculative decoding is not implemented.

## Earlier work

The project originally explored Qwen3 distillation, pruning, quantization search and CALM-style early exit. These are research background, not completed end-to-end experiments in the current result set. The Qwen3 distillation scripts remain in `edge_llm_inference/`.

The CPU-only synthetic controller demo in `prototype/` checks decision bookkeeping with hand-authored costs. It demonstrates logic but is not a model benchmark.
